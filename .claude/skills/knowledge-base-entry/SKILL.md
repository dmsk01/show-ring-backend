# Ведение `docs/knowledge/`

Каждая концепция, которую я объясняю пользователю (SQLAlchemy ORM, Alembic, aio-pika, Pydantic, JWT и т.д.), дублируется в `docs/knowledge/` — чтобы проект нёс живую документацию, независимую от истории чата. Пользователь сможет перечитать материал без поиска по переписке.

## Принцип

**Одна тема — один файл.** Имя в kebab-case, суффикс — на чём концепция (`sqlalchemy-orm-models.md`, `alembic-migrations.md`, `fastapi-dependency-injection.md`).

## Перед созданием нового файла

1. Прогляди `docs/knowledge/` (Glob или Read директории).
2. Грепни ключевой термин — может быть он уже упомянут в соседнем файле.
3. Если тема близка к существующему файлу (например `alembic-env-py.md` к `alembic-migrations.md`) — **обнови существующий**, добавив раздел H2, а не создавай дубликат.
4. Новый файл — только когда тема действительно самостоятельна.

## Структура файла

```markdown
# <Тема>

<1-2 предложения что это и зачем>

## <Концепция 1>

<Объяснение + пример кода>

## <Концепция 2>

...

## Ссылки

- [Официальная документация](https://...)
- [Статья/гайд, на который опирались](https://...)
```

### Правила оформления

- Заголовок H1 — ровно один, в начале файла.
- Подразделы H2 — по ключевым концепциям/терминам (одно имя термина = один H2, чтобы легко искать).
- Примеры кода — с указанием языка (` ```python `, ` ```sql `, ` ```bash `).
- Последний раздел всегда `## Ссылки` на официальную документацию.

## Стиль

- На **русском**.
- Конкретные фразы без воды. Не "это очень важная концепция", а "без этого миксина `obj.relation` в async-коде упадёт с ошибкой".
- Короткие примеры кода — 5-15 строк, показывающие ровно одну мысль.
- Настоящие имена (`Mapped`, `mapped_column`, `AsyncAttrs`), а не абстрактные ("аннотация типа", "колонка").

## Эталон

`docs/knowledge/sqlalchemy-orm-models.md` — хорошая референсная структура: H1-тема, несколько H2-концепций, раздел Ссылки в конце, короткие примеры кода с реальными именами классов.

## Что НЕ пишем в knowledge

- Статусы и прогресс по этапам → `docs/plans/stages/` или memory.
- Конкретные задачи пользователю → в чат через skill `task-format`.
- Баг-репорты, краткосрочные замечания → не в knowledge.
- Бизнес-правила платформы (как работает РКФ, классы выставок) → `docs/plans/` и специализированные места, не в knowledge (knowledge — про техническую механику стека).

## Как заглушить skill

Если пользователь спрашивает что-то концептуальное, но знает тему — skill всё равно релевантен (обновить/дополнить существующий файл). Если вопрос о состоянии проекта или конкретной задаче — skill не нужен.
