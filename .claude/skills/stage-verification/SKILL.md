# Проверка готовности этапа

Show Ring разбит на 15 этапов (см. `docs/plans/README.md`). Каждый файл `docs/plans/stages/stage-XX-<name>.md` заканчивается разделом **"Как проверить"** — это критерии готовности этапа. Skill проверяет каждый критерий против реального состояния репозитория и БД, а не по memory / CLAUDE.md.

## Когда вызывать

- Пользователь спрашивает "этап N готов?", "что осталось по этапу?", "можем переходить к следующему этапу?"
- После серии задач по одному этапу — перед переходом к следующему.
- Перед большим рефакторингом, когда нужно зафиксировать точку.

## Процесс

1. **Найди файл этапа.** `docs/plans/stages/stage-XX-*.md` (XX с ведущим нулём: 01, 02, ..., 15).
2. **Прочитай раздел "Как проверить"** в конце файла. Это упорядоченный список критериев.
3. **Для каждого критерия проведи реальную проверку через инструменты:**
   - Файл должен существовать → Glob / Read
   - Команда должна отработать (`alembic upgrade head`, `uvicorn app.main:app --reload`) → Bash, **только с разрешения пользователя**
   - Endpoint должен возвращать конкретный JSON → curl / HTTP-запрос, с разрешения
   - Таблица в БД → `docker exec postgres psql -U show_ring -d show_ring -c "\d <table>"`
4. **НЕ доверяй**:
   - "Текущий статус" в CLAUDE.md — это снимок на момент записи
   - `memory/project_state.md` — персональный снимок, может устареть
   - Последним сообщениям в чате — пользователь мог что-то откатить
5. **Отчитайся в структурированном виде** (см. ниже).
6. **Если есть недоделки** — оформи каждую как отдельную задачу через skill `task-format`.

## Формат отчёта

```markdown
**Этап N — <название>**: X из Y готово

- [x] `<критерий 1>` — <подтверждение: файл / команда / запись в БД>
- [x] `<критерий 2>` — <подтверждение>
- [ ] `<критерий 3>` — <чего не хватает>
- [ ] `<критерий 4>` — не проверено (требует запуска команды, нужно разрешение)
```

### Примеры строк отчёта

- `[x] alembic upgrade head — без ошибок. Последняя миграция 25574303691a применена, таблица users видна в БД.`
- `[ ] GET /health → {"status":"ok","db":"connected"} — endpoint ещё не реализован в app/main.py.`
- `[x] В PostgreSQL видна таблица users — \d users показывает колонки id/email/hashed_password/is_active/role/created_at/updated_at.`

## Разрешения

Проверки делятся на три группы:

| Тип | Инструмент | Нужно ли спрашивать |
|-----|-----------|----|
| Наличие файла, grep кода | Read / Glob / Grep | Нет, read-only |
| Запись в БД существует | `docker exec postgres psql ...` | Обычно нет — уже в allowlist |
| Запуск сервера / миграции | `uvicorn`, `alembic upgrade` | **Да, всегда спрашивать** |

Если проверка требует запуска — сначала пометить `[ ] не проверено (требует запуска)` и отдельно спросить разрешение.

## После отчёта

- Если всё готово (X == Y) — зафиксировать факт: обновить memory `project_state.md`, предложить переход к следующему этапу (указав, какой это этап и где его файл).
- Если есть пробелы — оформить задачи через skill `task-format`, по одной на критерий или блоком, и уточнить у пользователя, с чего начать.

## Не делать

- Не выдавать вердикт "этап готов" по ощущениям из переписки.
- Не проверять критерии не из файла этапа (не добавлять "от себя" дополнительных требований).
- Не править файл этапа, чтобы "подогнать" критерии под реальность — если пункт устарел, сначала обсудить с пользователем.
