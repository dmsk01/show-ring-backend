# Постановка задачи (Show Ring)

Пользователь учится backend на этом проекте. Готовый код без объяснения для него — шум. Каждая задача подаётся в едином 6-пунктовом формате, чтобы он понимал **механику**, **API технологии** и **архитектурное место** того, что делает.

## Шаблон

### 1. Что делать
Конкретный путь к файлу и что в нём должно быть. Если задача затрагивает несколько файлов — разбить на блоки или на отдельные задачи.

### 2. Как это работает
Механика — 2-5 предложений. Опирается на официальную документацию или устоявшиеся практики. Если упоминается класс/функция — её реальное поведение, а не пересказ имени.

### 3. API технологии / примеры
Короткие примеры кода из API технологии, которая применяется в задаче. Показать ключевые вызовы, параметры, возвращаемые значения — чтобы пользователь видел, как работает инструмент, до того как начнёт писать свой код. 3-15 строк на пример, не больше 2-3 примеров.

### 4. Зачем это нужно
Место в архитектуре Show Ring: почему именно здесь, что ломается если этого нет, как связано с соседними модулями.

### 5. Ключевые термины / функции
Список названий (классов, функций, параметров) + 1-строчное описание каждого. Это точки для самостоятельного чтения документации.

### 6. Как проверить
Конкретная команда / HTTP-запрос / SQL-запрос / вывод в логе, который покажет что всё работает. Без этого пункта пользователь не знает, что ожидать.

## Anti-patterns

- **Готовый код без объяснения.** Если нет разделов 2-4 — это не постановка задачи, а подсказка.
- **Пропущен пункт 3 (API/примеры).** Без примеров API пользователь не понимает инструмент до написания кода.
- **Пропущен пункт 6.** Без способа проверки пользователь не поймёт, получилось или нет.
- **Несколько файлов одним абзацем.** Разбивать на блоки: `### Файл 1`, `### Файл 2`, или давать отдельными задачами.
- **Абстрактные термины.** `AsyncSession`, `async_sessionmaker` — да. "Сессия", "фабрика" без имён — нет.
- **Копипаст из тикета без адаптации.** Формулировки под уровень пользователя, не под жаргон.

## Пример хорошо поставленной задачи

> ### Задача: `app/database.py`
>
> **1. Что делать.** Создать файл `app/database.py` со следующими объектами:
> - `engine` — результат `create_async_engine(settings.database_url, echo=False)`
> - `async_session_maker` — результат `async_sessionmaker(engine, expire_on_commit=False)`
> - асинхронный генератор `get_db()` → `AsyncSession`
>
> **2. Как это работает.** `create_async_engine` создаёт пул async-соединений к PostgreSQL через asyncpg. `async_sessionmaker` — фабрика сессий: каждый HTTP-запрос берёт свежую сессию через `Depends(get_db)`. `expire_on_commit=False` нужен, чтобы после commit объекты не превращались в detached — иначе FastAPI не сможет сериализовать ответ.
>
> **3. API технологии / примеры.**
> ```python
> from sqlalchemy.ext.asyncio import create_async_engine, async_sessionmaker
>
> engine = create_async_engine("postgresql+asyncpg://...", echo=True)
> Session = async_sessionmaker(engine, expire_on_commit=False)
>
> async with Session() as session:
>     result = await session.execute(select(User))
>     users = result.scalars().all()
> ```
>
> **4. Зачем это нужно.** Это единая точка входа в БД. Роутеры не создают сессии вручную, а получают их через DI. Это делает код тестируемым (в тестах подменяется `get_db`) и позволяет иметь transactional scope на запрос.
>
> **5. Ключевые термины.**
> - `create_async_engine` — создаёт AsyncEngine с пулом коннектов
> - `async_sessionmaker` — фабрика AsyncSession (SQLAlchemy 2.0 API)
> - `expire_on_commit` — управляет состоянием объектов после commit
> - `AsyncSession` — async-версия сессии; методы `execute`, `commit`, `rollback` — корутины
>
> **6. Как проверить.** После создания:
> ```python
> python -c "import asyncio; from app.database import engine; asyncio.run(engine.dispose())"
> ```
> Если команда отработала без импорт-ошибок и подключения — файл корректен.

## Пример плохо поставленной задачи

> Создай database.py с async_sessionmaker. Нужно для работы с БД.

Почему плохо: нет содержимого, нет механики, нет проверки, нет терминов для гугла.

## Связанные skills

- **knowledge-base-entry** — если задача вводит новую концепцию (первая встреча с `AsyncSession`, `Alembic revision`, `Depends`), вызови этот skill чтобы зафиксировать объяснение в `docs/knowledge/`.
- **stage-verification** — после серии задач по одному этапу, вызови этот skill чтобы проверить выполнение критериев готовности.
