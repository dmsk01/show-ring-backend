# Бэкапы: pg_dump, ротация, правило 3-2-1

Как устроено резервное копирование ShowTail (сервис `backup` в
`docker-compose.prod.yml`, скрипты в `deploy/backup/`) и почему оно
устроено именно так.

## Что бэкапим и что — нет

Бэкапим то, что невосстановимо:

- **PostgreSQL** — вся бизнес-информация: пользователи, собаки, выставки,
  результаты. Потеря = смерть проекта.
- **MinIO** — файлы пользователей: фото животных, сгенерированные
  дипломы. Дипломы можно перегенерировать из БД, фото — нет.

НЕ бэкапим то, что восстановимо из ничего:

- **Redis** — кэш, rate-limit-счётчики, idempotency-ключи. После рестарта
  с пустым Redis всё продолжает работать (счётчики начнутся заново).
- **RabbitMQ** — транзитные очереди. Недоставленные события переживут
  сбой через transactional outbox (`outbox_events` лежит в PG и попадает
  в дамп) — dispatcher переотправит pending-события сам.

Ключевая идея: **бэкап на том же диске — это не бэкап**, а защита от
«уронил таблицу». От смерти диска/компрометации сервера защищает только
offsite-копия (см. правило 3-2-1 ниже).

## pg_dump: plain vs custom format

`pg_dump` умеет несколько форматов вывода:

```bash
pg_dump -d showtail > dump.sql          # plain: текстовый SQL
pg_dump -d showtail -Fc -f dump.dump    # custom: бинарный архив
```

Мы используем **custom (`-Fc`)**, потому что он:

- сжат изнутри (zlib) — в разы меньше plain;
- позволяет селективный restore: `pg_restore -t users dump.dump`
  вытащит одну таблицу, plain-дамп пришлось бы резать руками;
- проверяется на читаемость без восстановления:

```bash
pg_restore --list dump.dump > /dev/null  # exit 0 = архив цел
```

Последний пункт — в `backup.sh` сразу после дампа: молча битый бэкап
хуже отсутствующего, потому что с ним живёшь в ложной уверенности.

Важно: **версия клиента pg_dump должна быть не ниже версии сервера**.
Поэтому backup-образ собран от `postgres:17-alpine` — та же мажорная
версия, что и сервер в compose.

## Ротация: 7 дневных + 4 недельных

Хранить всё подряд нельзя (диск конечен), хранить один последний —
опасно (порча данных, замеченная через неделю, уже в единственном
бэкапе). Двухуровневая схема:

- **7 дневных** — откат на любой день последней недели;
- **4 недельных** (копия воскресного дампа) — откат до месяца назад
  с шагом в неделю.

Механика в `backup.sh` — сортировка по времени + отрезание хвоста:

```bash
# ls -1t: новые сверху; tail -n +8: всё начиная с 8-го; rm: удалить.
ls -1t /backups/postgres/showtail-*.dump | tail -n +8 | xargs -r rm -f
```

Глоб `showtail-*` не матчит `weekly-showtail-*` (имя должно начинаться
с `showtail-`), поэтому дневная и недельная политики не пересекаются.

## Правило 3-2-1

Классический стандарт надёжности бэкапов:

- **3** копии данных (боевая + 2 бэкапа);
- **2** разных носителя;
- **1** копия вне площадки (offsite).

Текущее состояние ShowTail: боевая БД + локальный `./backups` — это
«2 копии, 1 носитель, 0 offsite». Осознанный старт (решение спеки
2026-06-12): offsite включается **четырьмя строками в `.env`** без
правки кода:

```bash
BACKUP_S3_ENDPOINT=https://s3.storage.selcloud.ru
BACKUP_S3_ACCESS_KEY=...
BACKUP_S3_SECRET_KEY=...
BACKUP_S3_BUCKET=showtail-backups
```

После этого `backup.sh` начнёт зеркалить весь `/backups` во внешний
S3 после каждого локального бэкапа.

## Restore-учения

Бэкап, который ни разу не восстанавливали, — лотерея. Процедура учения
(гонять минимум раз в квартал и после изменений схемы бэкапа):

```bash
# 1. Отдельная БД, чтобы не трогать боевую
docker compose exec postgres createdb -U showtail showtail_restore

# 2. Восстановление дампа в неё
docker compose run --rm backup restore.sh \
    /backups/postgres/showtail-2026-06-12.dump showtail_restore

# 3. Проверка: количество строк ключевых таблиц совпадает с боевой
docker compose exec postgres psql -U showtail -d showtail_restore \
    -c "SELECT count(*) FROM users;"

# 4. Уборка
docker compose exec postgres dropdb -U showtail showtail_restore
```

Файлы MinIO восстанавливаются зеркалом в обратную сторону
(`mc mirror /backups/minio/<bucket> src/<bucket>`) — команды в шапке
`deploy/backup/restore.sh`.

`pg_restore` запускается с `--clean --if-exists` (дропнуть объекты перед
созданием — restore идемпотентен) и `--no-owner` (не тащить владельца
из дампа — дамп переносим между окружениями).

## Ограничения и апгрейд-путь

Суточный дамп = **RPO до 24 часов**: упавший в 23:00 сервер теряет всё
с 03:30 утра. Для текущего масштаба это приемлемо. Когда потеря дня
данных станет недопустимой (живые заявки на выставки за деньги) —
переходить на **WAL-архивацию** (point-in-time recovery): инструменты
[pgBackRest](https://pgbackrest.org/) или [wal-g](https://github.com/wal-g/wal-g).
Они дописывают журнал транзакций в хранилище непрерывно, RPO падает до
секунд. Схема каталогов и offsite-бакет при этом переиспользуются —
апгрейд не ломает текущую механику.
