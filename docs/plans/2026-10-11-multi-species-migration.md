# План миграции на мультивидовую платформу

**Дата:** 2026-10-11 · **Репозитории:** `show-ring-backend`, `show-ring-frontend` · **Статус:** план, работы не начаты.

## Зачем этот документ

Сейчас Show Ring обкатывается на собаках (РКФ / FCI). Позже на платформу придут кошки и, возможно, другие виды. Цель плана:

1. **Сейчас, пока есть только собаки**, сделать дешёвую подготовку (Фаза 0), чтобы потом не мигрировать данные и не переписывать ядро выставок.
2. Зафиксировать, **что и где** придётся менять при подключении нового вида (Фазы 1–3), и какие решения принять заранее.

Обещания «выставки собак и кошек» из интерфейса убраны (show-ring-frontend PR #8). Вернуть их — последний тикет Фазы 1 (MS-24).

## Как читать

- **Фаза 0 — подготовка сейчас.** Поведение для собак не меняется, у пользователей ничего не видно. Делать можно по одному тикету, в любом порядке внутри фазы, кроме указанных зависимостей.
- **Фаза 1 — второй вид (кошки), MVP.** Кошки работают на тех же механизмах, что и собаки: виды разделены, есть свои справочники и подписи.
- **Фаза 2 — правильные кошачьи выставки.** Специфика фелинологии: кастраты, окрасы EMS, своя система титулов и номинаций.
- **Фаза 3 — любые виды.** Добавление вида — это данные и набор правил, без правок ядра.
- **Оценка:** S — до дня, M — 2–4 дня, L — неделя и больше. Оценки грубые, для одного разработчика.
- **Репо:** BE — бэкенд, FE — фронтенд, DATA — сиды и справочники, DOC — документы и решения.
- В каждом тикете первый пункт чек-листа — тест, который фиксирует требование (TDD, как в ревью 2026-10-09).

## Решения, которые нужно принять до Фазы 1

Это не код, но без них Фаза 1 начнётся с переделок. Оформить как ADR (MS-11).

1. **Одна выставка — один вид.** Рекомендация: да, на старте. Смешанные выставки (общая площадка, разные виды) потребуют BIS по видам, раздельных рингов и каталогов. Отложить до реального запроса организаторов.
2. **Внутреннее имя «dog».** Рекомендация: таблицы и модели **не переименовывать** (`dogs` остаётся). Миграция имён таблиц рискованна и ничего не даёт пользователю. В новых API и в интерфейсе — «животное» (`/animals`), старые `/dogs` оставить как есть.
3. **Правила выставок как подключаемый набор по виду (ruleset).** Ядро вызывает интерфейс, реализация FCI-собак — первая. Без этого кошачья логика расползётся по `if species == 'cat'`.
4. **Фелинологическая система.** FIFe, WCF или российская клубная (например, по правилам конкретной федерации) — от этого зависят классы, титулы, номинации, ранги и коды окрасов. Решение за владельцем продукта, нужен эксперт-фелинолог и официальные документы системы.
5. **URL публичных страниц.** Варианты: `/dogs/{id}` и `/cats/{id}` или общий `/animals/{id}`. Рекомендация: общий `/animals/{id}` для новых видов, `/dogs/{id}` — постоянный редирект или оставить (SEO уже проиндексировано).
6. **Выкатка через фича-флаг.** Флаги уже есть (бэкенд `app/routers/feature_flags.py`, фронт `FeatureFlagsProvider`): `species_cat` скрывает всё кошачье до готовности.

## Фаза 0. Подготовка сейчас

### <a id="ms-01"></a>MS-01 · Фаза 0 · BE · M · Вид у выставки

**Где:** `app/models/show.py:76` (`Show`), `:134` (`breeds`); `app/schemas/show.py` (`ShowBase`, `ShowCreate`); `app/services/show.py:80–90` (`create_show`, `breed_ids`), `:450–465` (проверки записи); `show_judges` (`app/models/show.py`, назначение на породу или группу); миграция Alembic.

**Проблема:** выставка не знает свой вид. Вид выводится только из пород участников. Всепородная выставка (пустой `breed_ids`) пустит любую породу любого вида, BIS считается на всю выставку, классы в форме нельзя отфильтровать заранее.

**Решение:**
- Колонка `shows.animal_type_id` (FK `animal_types`, `ondelete=RESTRICT`), миграция: добавить nullable → заполнить видом `dog` → сделать NOT NULL.
- `ShowCreate.animal_type_id` необязательный, по умолчанию — вид `dog` (код из настроек). В ответе `ShowResponse` — `animal_type_id` и `animal_type_code`.
- Проверки: породы из `breed_ids` — того же вида (`show_breed_animal_type_mismatch`); судья на породу или группу — того же вида; запись — порода собаки того же вида, что выставка (`entry_animal_type_mismatch`).
- Смена вида у выставки с записями запрещена.

**Чек-лист:**
- [ ] Тесты: всепородная выставка вида `dog` не принимает животное другого вида; `breed_ids` другого вида → 422; смена вида с записями → 409.
- [ ] Миграция с backfill и откатом; `pytest`, `ruff`, `pyright` зелёные.
- [ ] Фронт не ломается: поле в ответе новое, в запросе необязательное.

**Учесть:** ранг (`ShowRank`) пока общий, см. MS-06. BIS и BIG на выставке одного вида корректны без доработок.

### <a id="ms-02"></a>MS-02 · Фаза 0 · BE · S · Оценка результата — только своего вида

**Где:** `app/services/result.py:331–334` (загрузка `grade`, проверка только на существование).

**Проблема:** сейчас оценок одного вида нет, но после сида кошачьих оценок через API можно будет поставить собаке оценку кошачьей системы.

**Решение:** после загрузки `grade` сверить `grade.animal_type_id` с `cls.animal_type_id` (класс записи уже проверен по виду в `show.py:455`); иначе `ValueError("grade_animal_type_mismatch")` → 422.

**Чек-лист:**
- [ ] Тест: оценка другого вида → 422 `grade_animal_type_mismatch`.
- [ ] Перевод кода ошибки во фронте (`src/sections/show/show-errors.ts`).

### <a id="ms-03"></a>MS-03 · Фаза 0 · BE · S · Родители — только того же вида

**Где:** `app/services/dog.py:36–60` (проверки родителей: существование, пол, сам себе, цикл); добавление потомка — `app/services/dog.py` (`add_descendant`).

**Проблема:** при правке собаки и при добавлении потомка вид не сверяется. С кошками в базе отцом собаки можно будет указать кота.

**Решение:** сравнить вид породы родителя с видом породы животного (`father_animal_type_mismatch`, `mother_animal_type_mismatch`). Породу не сверять: у собак межпородные родители допустимы (метисы, разновидности), у помёта порода уже проверяется отдельно.

**Чек-лист:**
- [ ] Тест: родитель другого вида → 422 (создание, правка, добавление потомка).
- [ ] Перевод ошибки на фронте (`src/sections/dog/dog-relatives.tsx`, форма собаки).

**Учесть:** фронт-поиск родителей (`src/sections/dog/parent-options.ts`) после MS-04 фильтровать и по виду.

### <a id="ms-04"></a>MS-04 · Фаза 0 · BE · S · Вид в ответах API и фильтр по виду

**Где:** `app/schemas/dog.py:63` (`DogResponse`), схемы помёта, объявления, выставки; `app/routers/dogs.py:95–130` (`list_dogs`), `app/repositories/dog.py:35–60` (`_dog_filter_stmt`); аналогично `litters`, `classifieds`, `shows`.

**Проблема:** фронт не знает вид животного без отдельной загрузки породы и не может запросить «только собаки».

**Решение:**
- В ответах: `animal_type_id` и `animal_type_code` (через породу, одним join — без N+1).
- Фильтр `animal_type` (код или id) в списках `/dogs`, `/litters`, `/classifieds`, `/shows`.

**Чек-лист:**
- [ ] Тесты: поле в ответе; фильтр отсекает другой вид.
- [ ] Обновить типы фронта (`src/types/dog.ts`, `litter.ts`, `classified.ts`, `show.ts`) и тест контрактов `src/types/__tests__/contracts.test.ts`.

### <a id="ms-05"></a>MS-05 · Фаза 0 · BE · L · Реестр наборов правил по виду

**Где:** `app/services/show_rules.py:36–196` (константы классов, титулов, ранга), `:238` (`compute_class_titles`), `:297–349` (BOB, BIG, BIS); `app/services/checkin_rules.py:28–32, 85–87` (документы); `app/services/result.py` (выдача титулов, флаги лучших, `:387` — проверка `cw`); `REQUIRES_DOCS_NOTES` (`show_rules.py:39`).

**Проблема:** правила FCI-собак — набор констант и функций без абстракции. Второй вид придётся встраивать условиями по всему коду выставок и чек-ина.

**Решение:**
- Интерфейс `ShowRuleSet` (Protocol): доступные классы по возрасту (и, в будущем, по кастрации), документы для класса, титулы за результат в классе, титулы лучших в породе, допустимые номинации, переходы статуса выставки.
- `app/services/rules/__init__.py` — реестр `{'dog': FciDogRules()}`; `get_ruleset(animal_type_code)`.
- Текущий код переезжает в `app/services/rules/fci_dog.py` **без изменения поведения**; `show_rules.py` и `checkin_rules.py` становятся тонкими обёртками или удаляются после переноса вызовов.
- Вызывающий код получает набор правил по виду выставки (после MS-01) или по виду породы.

**Чек-лист:**
- [ ] Все текущие тесты выставок, результатов и чек-ина зелёные без изменений ожиданий (регрессионная сеть).
- [ ] Тест реестра: неизвестный вид → понятная ошибка; `dog` → FCI-реализация.
- [ ] Ни одного кода класса или титула (`'working'`, `'cac'` и т.п.) вне `rules/fci_dog.py` — проверка в тесте (поиск по исходникам, как сторож i18n во фронте).

**Учесть:** делать после MS-01 (вид выставки) — так набор правил берётся с выставки, а не угадывается по первой записи. Флаги лучших в `ShowResult` пока не трогать — см. MS-23.

### <a id="ms-06"></a>MS-06 · Фаза 0 · BE · S · Ранги выставок по виду

**Где:** `app/models/reference.py:197–215` (`ShowRank`, комментарий «у РКФ ранги одинаковы для всех видов»); `app/routers/references.py` (`/references/show-ranks`); проверка в `create_show`.

**Проблема:** у фелинологических систем свои ранги (CACIB у FIFe — не то же, что у FCI). Общий справочник рангов смешает их.

**Решение:** `ShowRank.animal_type_id` nullable: NULL — ранг общий (как сейчас), иначе — только для вида. Фильтр в API; при создании выставки — ранг общий или того же вида.

**Чек-лист:**
- [ ] Тест: ранг другого вида для выставки → 422; общий ранг подходит любому виду.
- [ ] Существующие ранги остаются общими (миграция без backfill).

### <a id="ms-07"></a>MS-07 · Фаза 0 · FE · M · Явный вид в справочниках

**Где:** `src/actions/reference.ts:22` (`useGetBreeds`) и хуки групп, классов, титулов, оценок; формы: `src/sections/dog/dog-create-edit-form.tsx`, `src/sections/litter/litter-create-edit-form.tsx`, `src/sections/classified/classified-create-edit-form.tsx`, `src/sections/show/show-create-edit-form.tsx` (список пород), фильтры каталогов (`dog-table-toolbar.tsx`, витрины); `src/global-config.ts`.

## Что учесть в дальнейшем

- **Любой поиск справочника по коду — только в рамках вида.** Коды уникальны внутри вида, а не глобально. Это уже соблюдается в `show_rules.py`, правило нужно сохранять в новом коде (сторож из MS-05).
- **Одна выставка — один вид**, пока ADR не решит иначе. Смешанные выставки затрагивают BIS, ринги, каталог, расписание и PDF.
- **Судьи:** назначение уже идёт по породе или группе, то есть по виду. Квалификация судьи по виду и системе — отдельная задача, если понадобится проверка.
- **Межвидовые связи запрещены:** родители (MS-03), помёт (уже по породе), запись на выставку (MS-01), оценки и титулы (MS-02, существующие проверки).
- **Данные не переименовывать:** таблицы `dogs*` остаются. «Животное» — в интерфейсе и новых API. Это осознанный долг ради безопасной миграции.
- **Регистрационные номера:** уникальность по книге (MS-10), а не глобально.
- **i18n:** все видовые слова — в `species.json`, с падежами; сторож запрещает их вне этого файла (MS-08).
- **SEO:** старые URL `/dogs/{id}` проиндексированы — не ломать.
- **Маркетинг:** обещать новый вид только после включения флага (MS-24). Сейчас тексты говорят только о собаках.
- **Правовое:** 152-ФЗ от вида не зависит. Пользовательское соглашение и правила площадки упоминают выставки — проверить формулировки при запуске нового вида.
- **Правила систем меняются:** хранить у выставки версию правил, по которой она проводилась (MS-22).
- **Эксперт предметной области** нужен на Фазах 1–2 сильнее разработчика: без него справочники и правила будут неверными.
