# Этап 20 — Персональные данные и правовые документы (152-ФЗ)

## Контекст

На фронте опубликованы Пользовательское соглашение, Политика
конфиденциальности, Согласие на обработку ПДн и Согласие на распространение
ПДн (`show-ring-frontend/src/sections/legal/`). Правовой аудит
(`show-ring-frontend/docs/plans/legal-compliance-plan.md`) показал, что
бэкенд не выполнял того, что в них обещано: согласия нигде не фиксировались,
контакты публиковались без согласия, удалить аккаунт было нельзя, сроки
хранения не соблюдались, реклама не маркировалась.

**Решения (зафиксированы):**
- Площадка — **информационный посредник** (ч. 3 ст. 17 149-ФЗ, ст. 1253.1
  ГК РФ). Не принимаем оплату за сделки между пользователями: иначе сервис
  становится владельцем агрегатора (Закон о защите прав потребителей) и
  попадает под 289-ФЗ о платформенной экономике.
- Согласие на обработку ПДн — **отдельная отметка**, не часть фразы
  о принятии Соглашения (ч. 1 ст. 9 152-ФЗ в ред. 156-ФЗ, с 01.09.2025).
- Согласие на распространение (ст. 10.1) — **по каждой публикации**
  (питомник, объявление), а не «вообще». Молчание ≠ согласие (ч. 8):
  у существующих публикаций контакты скрыты до явного включения.
- Аккаунт **обезличивается, а не удаляется физически**: на `users`
  ссылаются выставки, записи, судейство и рекламные кампании (FK RESTRICT).
- Регистрация по email в проде выключена и служит тестам, поэтому согласия
  там необязательны; недостающие согласия запрашивает фронт после входа.

## Что сделано

### Фаза A — Журнал согласий
- Модель `app/models/consent.py` → таблица `user_consents`
  (`kind`, `revision`, `target_id`, `granted_at`, `revoked_at`, `ip`, `user_agent`).
- Сервис `app/services/consent.py`: `grant` (идемпотентно по редакции),
  `revoke`, `list_active`, `missing_required`, `set_publication_consent`.
  Редакции документов — `CURRENT_REVISIONS`, синхронно с `LEGAL_REVISIONS`
  во фронте.
- `POST /auth/verify-code` принимает `accept_terms` и `personal_data_consent`.
  Новый номер без обеих отметок → **400 `consent_required`**, аккаунт не
  создаётся. Проверка идёт после сжигания кода — иначе по ответу можно
  перебирать занятые номера.
- `GET / POST /users/me/consents`, `DELETE /users/me/consents/{kind}`.
  `terms` отдельно не отзывается (**400 `use_account_deletion`**),
  публикационные — только переключателем (**400 `use_publication_toggle`**).

### Фаза B — Контакты только с согласия (ст. 10.1)
- Колонка `contacts_public` у `kennels` и `classifieds`
  (`server_default=false`).
- `app/utils/public_contacts.hide_private_contacts` — в публичных ручках
  `contact_phone`, `contact_email` (у питомника ещё `website`) = `null`,
  если флаг выключен и смотрит не владелец/админ.
- Включить флаг может только владелец (**403 `consent_owner_only`**);
  каждое переключение пишется в журнал с `target_id` публикации.
- Переключение видимости у объявления не отправляет его на повторную
  модерацию.

### Фаза C — Удаление аккаунта
- `POST /users/me/delete` (`app/services/account_deletion.py`):
  повторная аутентификация кодом из `/users/me/reauth/send-code` или паролем.
- Удаляются: профиль, роли, сессии, токены, согласия, объявления,
  обращения в поддержку, подписки, уведомления, сканы документов собак
  (и их объекты в S3), аватар. У питомника стираются контакты и сайт.
  Собаки остаются как исторические записи с `owner_id = NULL`.
- `users`: `phone=NULL`, `email=deleted-<id>@deleted.invalid` (CHECK
  требует email или phone), `is_active=False`, `deleted_at=now()`.
- Блокеры: **409 `active_shows`** (организатор непрошедших выставок),
  **409 `active_ad_campaigns`**.
- `app/utils/names.full_name` для удалённого → «Удалённый пользователь»
  (каталоги, дипломы, авторы блога).

### Фаза D — Сроки хранения
- `app/services/retention.py` + задача `enforce_data_retention`
  (ежедневно в 03:30): `security_audit_logs` старше 365 дней удаляются,
  в `ad_events` старше 183 дней обнуляются `ip`, `user_agent_hash`,
  `user_id`.
- `docker-compose.prod.yml`: ротация логов `json-file` (5 × 20 МБ) у всех
  сервисов — в логах nginx и api есть IP посетителей.

### Фаза E — Реклама и письма
- `ad_banners.erid`, `ad_campaigns.advertiser_name/advertiser_inn`.
  `/ads/serve` не отдаёт баннер без `erid` и возвращает `label="Реклама"`,
  `erid`, сведения о рекламодателе.
- `render_email` для шаблонов из `EventType` добавляет подвал «Отписаться
  или изменить подписки» со ссылкой на `/dashboard/notifications`.

## Как проверить

```bash
alembic upgrade head
pytest -q                     # 399 passed на 04.10.2026
ruff check . && pyright app worker
```

Вручную:
1. Вход по новому номеру без отметки согласия → 400 `consent_required`.
2. Питомник с контактами → анонимный `GET /kennels/{id}` отдаёт `contact_phone: null`.
3. `POST /users/me/delete` с кодом → `GET /users/me` = 401, номер свободен для новой регистрации.
