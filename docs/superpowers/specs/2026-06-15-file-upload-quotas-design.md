# Дизайн: защита загрузки файлов от перегрузок (квоты + backpressure)

**Дата:** 2026-06-15
**Статус:** утверждён, готов к плану реализации

## Проблема

`POST /files/upload` сейчас защищён только общим edge-лимитом nginx (`general=20r/s` по IP)
и валидацией одного файла (magic bytes + `max_upload_size_bytes` = 10 МБ). Прикладной
защиты нет:

- нет специфичного для загрузки лимита (загрузка в ~100× дороже, чем GET справочника,
  но лимит общий);
- нет квоты на пользователя — залогиненный юзер в рамках 20 r/s за час нальёт десятки
  тысяч файлов и забьёт диск MinIO («задудосили хранилище»);
- нет backpressure: всплеск легитимных юзеров может открыть сотни параллельных
  соединений к MinIO и положить его.

Цель — закрыть оба сценария (злонамеренный флуд и естественный всплеск) слоями
defence-in-depth, опираясь на уже существующую инфраструктуру.

## Что уже есть (не трогаем)

- **Слой 1 (edge):** `deploy/nginx/nginx.conf` — `limit_req_zone general=20r/s`,
  `auth=5r/s`, `client_max_body_size 10m`.
- **Слой 2 (инструмент app rate-limit):** `app/middleware/progressive_ban.py` —
  sliding window + экспоненциальный бан на Redis (атомарный Lua). Готовый инструмент.
- **Валидация одного файла:** `app/services/file_storage.py` — magic bytes + лимит
  размера на лету (защита от OOM).
- **Слой 5 (очередь воркера):** консьюмер `image_task` уже с `prefetch_count=1`
  (`worker/main.py:217`) — воркер берёт по одной задаче, память Pillow не взрывается.
  **Менять не нужно.**

## Модель тиров

Три тира пользователя, от строгого к свободному. Резолвится чистой функцией
`resolve_upload_tier(user) -> UploadTier`:

| Тир | Условие | Кто это |
|-----|---------|---------|
| `untrusted` | `is_email_verified=False AND is_phone_verified=False` | свежий/неверифицированный аккаунт — главная мишень абьюза |
| `standard` | верифицирован (email **или** телефон), без роли `breeder` | обычный покупатель |
| `breeder` | роль `breeder` **или** есть запись в `kennels.owner_id` | владелец питомника |

Роли уже грузятся к юзеру (`User.roles`). Владение питомником определяется наличием
роли `breeder` как достаточного признака; при необходимости — дополнительный `EXISTS`
по `kennels.owner_id`.

### Сигнал доверия: `is_phone_verified`

Телефон-OTP — основной способ верификации, поэтому `is_email_verified` как
единственный сигнал не годится (телефонные юзеры остались бы `untrusted` навсегда).

- Добавляем колонку `users.is_phone_verified` (bool, `default False`,
  `server_default 'false'`).
- В `app/services/otp_auth.py::verify_otp_code` при успешной верификации/создании
  юзера ставим `is_phone_verified = True` (факт владения номером доказан вводом кода).
- Признак доверия = `is_email_verified OR is_phone_verified`.

Решение — сделать верификацию явной первоклассной сущностью, а не побочным эффектом
наличия номера (устойчиво к будущему флоу смены телефона).

## Слой 3: квоты на пользователя

### Где считаем: в БД, не в Redis

Загрузка — редкая и дорогая операция (S3 put + задача Pillow), один `COUNT`/`SUM` на
её фоне ничтожен. БД — источник истины: квоту нельзя обойти сбросом Redis, и она
переживает падение Redis. Redis-sliding-window (`progressive_ban`) хорош для частых
дешёвых эндпоинтов (auth, поиск), где DB-хит на запрос дорог — здесь не тот случай.

### Две оси квоты

Перед загрузкой (после валидации файла, до `put_object`):

1. **Суточная частота:**
   `used_today = COUNT(uploaded_files WHERE uploaded_by = user AND created_at > now() - 24h)`
   `if used_today >= tier.daily_limit → 429`
2. **Общий объём:**
   `used_bytes = SUM(size_bytes) по всем uploaded_files юзера` (без временного окна —
   это «сколько всего занимает»). `if used_bytes + new_file_size > tier.max_storage_bytes → 413`

Индекс: `ix_files_uploaded_by_created (uploaded_by, created_at)` — покрывает обе агрегации.

### Дефолтные лимиты (стартовые значения, редактируются админом)

| Тир | Загрузок/сутки | Объём всего |
|-----|----------------|-------------|
| `untrusted` | 5 | 50 МБ (`52428800` байт) |
| `standard` | 30 | 500 МБ (`524288000` байт) |
| `breeder` | 200 | 2.5 ГБ (`2684354560` байт) |

## Ошибка с «периодом охлаждения»

При исчерпании суточной частоты — `429 Too Many Requests`, инфо о cooldown и в
заголовке, и в теле:

```
Retry-After: <секунд до освобождения слота>
```
```json
{
  "detail": "Дневной лимит загрузок исчерпан",
  "tier": "untrusted",
  "limit": 5,
  "used": 5,
  "retry_after_seconds": 3600,
  "reset_at": "2026-06-16T09:00:00Z"
}
```

`reset_at` считается честно по скользящему окну:
`reset_at = (самая старая загрузка в окне).created_at + 24h` — слот освободится ровно
когда она выпадет из суток. `retry_after_seconds = reset_at - now`.

Исчерпание объёмной квоты — отдельная ошибка (cooldown неприменим, объём сам не
освобождается): `413 Request Entity Too Large` с телом `{detail, tier,
max_storage_bytes, used_bytes}` и подсказкой удалить старые файлы. Без `Retry-After` —
ожидание не поможет, нужно действие пользователя.

## Слой 4: backpressure к хранилищу

Чтобы всплеск легитимных юзеров не открыл сотни параллельных соединений к MinIO:
процессный `asyncio.Semaphore(N)` вокруг тяжёлой части загрузки (чтение тела +
`put_object`) в `file_storage`. Если за таймаут слот не освободился → `503` +
`Retry-After`. Лимитирует *одновременность*, а не суммарный объём. `N` и таймаут —
в конфиг (`settings`).

## Слой 5: очередь воркера

Уже закрыто `prefetch_count=1` на `image_task`. Дополнительно суточная квота (слой 3)
косвенно ограничивает число задач на юзера — бесплатный побочный эффект.

## Админский CRUD лимитов

Лимиты тиров — редактируемые **данные**, не константы. Хранение — таблица PostgreSQL
(вариант A): авторитетный источник, переживает падение Redis, в одном месте со
счётчиком квоты (единая консистентность), CRUD ложится буквально на таблицу.

### Таблица `upload_quota_tiers`

3 строки, засеяны миграцией; ключ = enum тира.

| Колонка | Тип | Назначение |
|---------|-----|------------|
| `tier` | enum/str (PK) | `untrusted` / `standard` / `breeder` |
| `daily_limit` | int | загрузок в сутки |
| `max_storage_bytes` | bigint | потолок общего объёма |

### API (под `require_any_role("admin")`)

```
GET  /admin/upload-quotas            — список конфигов всех тиров
PUT  /admin/upload-quotas/{tier}     — изменить лимиты тира
```

Тело PUT:
```json
{ "daily_limit": 5, "max_storage_bytes": 52428800 }
```

Тиры — фиксированный набор (выводятся из ролей), поэтому create/delete не нужны:
CRUD здесь = list + update трёх известных конфигов (та же форма, что у переключателя
`feature_flags`). `{tier}` валидируется по enum — неизвестный → 404.

Чтение лимитов на upload — прямой запрос в БД (загрузка редкая, кеш не обязателен;
если профилирование покажет нужду — добавим короткий in-memory кеш как у `FlagService`).

## Поведение при сбоях

- **Redis недоступен:** квота и лимиты на БД — работают полностью. Затрагивается
  только семафор слоя 4 (он процессный, Redis не нужен) и edge-лимит nginx (отдельная
  подсистема). То есть основная защита от перегрузки хранилища от Redis не зависит.
- **MinIO недоступен:** существующее поведение — `503` из `file_storage` (не регрессим).

## Компоненты и границы

| Юнит | Ответственность | Зависит от |
|------|-----------------|-----------|
| миграция `is_phone_verified` + правка `verify_otp_code` | явный сигнал доверия | — |
| `resolve_upload_tier(user)` | user → тир | роли юзера |
| модель `UploadQuotaTier` + миграция-сид | хранение лимитов | — |
| репозиторий квот (`count_today`, `sum_bytes`, `get_tier_config`) | агрегации и чтение лимитов | БД |
| сервис проверки квоты | собирает тир+лимиты+факт, решает разрешить/429/413, считает cooldown | резолвер, репозиторий |
| семафор в `file_storage` | backpressure к MinIO | — |
| роутер `admin/upload-quotas` | CRUD лимитов | сервис/репозиторий квот |
| правка `POST /files/upload` | вызвать проверку квоты до S3 + захват семафора | сервис квоты, file_storage |

## Критерии приёмки

1. Миграции применяются; `users.is_phone_verified` существует, `verify_otp_code`
   ставит его в `True`; таблица `upload_quota_tiers` засеяна тремя строками.
2. `untrusted`-юзер на (N+1)-й загрузке за сутки получает `429` с корректными
   `Retry-After` и `reset_at`.
3. Превышение `max_storage_bytes` → `413` с инфо об объёме.
4. `breeder` имеет более высокие лимиты, чем `standard`, тот — выше `untrusted`.
5. Админ через `PUT /admin/upload-quotas/{tier}` меняет лимит, новое значение
   применяется к последующим загрузкам; не-админ получает `403`.
6. При остановленном Redis квота продолжает работать (тест на fail-сценарий).
7. Семафор ограничивает число одновременных загрузок (тест на превышение → `503`).

## Тестирование

- Юнит: `resolve_upload_tier` для всех комбинаций (верифицирован/нет × роль).
- Юнит: расчёт `reset_at`/`retry_after_seconds` по фикстуре загрузок.
- Интеграция: суточная квота (429 + тело), объёмная квота (413), CRUD лимитов (admin
  vs не-admin), `is_phone_verified` после OTP.
- Интеграция: квота при недоступном Redis.

## Вне области (follow-up)

- Честный потоковый upload (`upload_fileobj`/multipart) при подъёме лимита размера.
- In-memory кеш лимитов (только если профилирование покажет нужду).
- Квоты на скачивание/трафик (egress) — отдельная тема.
