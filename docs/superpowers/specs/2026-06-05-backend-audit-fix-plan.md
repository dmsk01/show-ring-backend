## Находки

### C1 — Пустой `SECRET_KEY` поднимается молча → подделываемый JWT  ·  Critical

**Где.** `app/config.py:9` — `secret_key: str` (принимает пустую строку);
`docker-compose.yml` — `SECRET_KEY: ${SECRET_KEY}` (без `:-default`);
`.env.example` / `.env.compose.example` — плейсхолдер `change-me-in-production`.

**Что не так.** Поле `secret_key` обязательное, но `""` — валидная строка:
приложение стартует с пустым ключом. Доступы (access JWT) подписываются HS256
этим ключом; при пустом/предсказуемом ключе токен можно подделать
(`sub=<любой user_id>`, `type=access`) и аутентифицироваться кем угодно —
полный обход авторизации. Compose прокидывает `${SECRET_KEY}` без дефолта, так
что незаданная переменная → пустой ключ.

**Доказательство.** В живом контейнере прямо сейчас `printenv SECRET_KEY` →
пусто. То есть запущенный стек подписывает токены пустым ключом.

**Влияние.** Подделка любого access-токена → вход под любым пользователем/
админом. Если конфиг доедет до prod без ключа — катастрофа; в dev — уже так.

**Фикс.** В `Settings` добавить валидатор: запрет пустого, `change-me-*` и
слишком короткого (< 32 симв.) `secret_key` при `debug=False` (в dev —
предупреждение). Приложение должно падать на старте с внятной ошибкой, а не
подниматься небезопасным. Отдельно (вне кода): задать реальный `SECRET_KEY` в
`.env` запущенного окружения.

### H1 — Черновики блога публично видны  ·  High

**Где.** `app/routers/posts.py` — `list_posts` (`publish: PostPublish | None =
Query(None)`) и `get_post` (lookup по slug без фильтра статуса);
`app/repositories/post.py` — `list_page`/`get_by_slug` не ограничивают `publish`.

**Что не так.** Read блога публичный (для лендинга/SEO — by design). Но:
- `GET /posts` без `?publish=` отдаёт **и draft, и published** анонимам;
- `GET /posts/{slug}` отдаёт draft-пост любому, кто знает/угадал slug.

Неопубликованный контент (черновики, утечки анонсов) виден наружу и может
попасть в поисковый индекс.

**Влияние.** Преждевременная утечка контента; SEO-замусоривание черновиками.

**Фикс.** Публичный read — только `published`. Просмотр черновиков — под
`require_any_role("admin","organizer")` (либо параметр `?publish=` уважается
только для авторизованного writer'а, иначе игнорируется и форсится `published`).
В `related` фильтр `published` уже стоит — выровнять остальное под него.

### M1 — Публичные list/search без rate-limit  ·  Medium

**Где.** `check_rate_limit` используется только в роутерах
`ads, auth, classifieds, references, users`. НЕ используется в
`posts, dogs, kennels, litters, shows, results, documents, notifications,
support, files, tasks`.

**Что не так.** Тяжёлые публичные ручки без лимита — DoS/abuse-вектор. Самые
показательные:
- `GET /posts?query=` — `ILIKE %query%` по title/description (seq-scan, CPU) на
  анонимной ручке;
- публичные списки `GET /dogs`, `/kennels`, `/litters` с фильтрами/сортировкой.

Для поиска объявлений ровно эта проблема уже закрыта (bug_213: 30 req/min на IP
на `/classifieds/search`), но паттерн не перенесён на блог и остальные.

**Влияние.** Дешёвый анонимный флуд греет PostgreSQL/CPU; усиливается на
query-ручках с `ILIKE`/сортировкой.

**Фикс.** Добавить `check_rate_limit` (по IP) на публичные query/search-ручки —
в первую очередь `GET /posts` (особенно с `query`), затем list-ручки
`dogs/kennels/litters`. Лимит порядка существующего поиска (30–60/min).

### M2 — in_app-уведомления завязаны на email-подписки  ·  Medium

**Где.** `worker/handlers/events_handler.py:186` (`find_subscribers(..., channel=
NotificationChannel.email)`) и цикл `for sub, user in subscribers:` — внутри него
создаётся и email-, и in_app-уведомление (`_create_in_app_notification`,
строки 266–275).

**Что не так.** Список получателей берётся ТОЛЬКО по email-подпискам, а in_app
создаётся для каждого из них. Следствия:
- пользователь с подпиской `channel=in_app` (но без email-подписки) **не получит
  ничего** — его нет в выборке;
- пользователь с email-подпиской **принудительно** получает ещё и in_app, даже
  если канал колокольчика ему не нужен.

То есть канал доставки in_app фактически не управляется подписками in_app.

**Влияние.** Неверная адресация realtime-уведомлений: часть пользователей не
получает колокольчик, часть получает его без запроса.

**Фикс.** Развязать каналы: получателей in_app брать по in_app-подпискам
(отдельная выборка `find_subscribers(channel=in_app)`), email — по email. Либо
объединение с дедупом по user_id и пер-канальной логикой. Уточнить замысел
этапа 16 (возможно, in_app задумывался как зеркало email — тогда зафиксировать
это явно, но всё равно покрыть in_app-only подписчиков).

### L1 — Любой writer правит/удаляет любой пост блога  ·  Low

**Где.** `app/routers/posts.py` — `update_post`/`delete_post` под
`require_any_role("admin","organizer")`, но без проверки `author_id == user.id`.

**Что не так.** Organizer может отредактировать/удалить пост другого organizer'а.
Для общей CMS это может быть осознанно (в отличие от объявлений/собак, где
проверка владельца есть). Нужно подтвердить замысел.

**Фикс (если не by design).** Не-admin может менять только свои посты; admin —
любые. Если by design — задокументировать в плане этапа 17.

---

### L2 — Общая таблица токенов verify/email-change без типа  ·  Low

**Где.** `app/services/auth.py` — `verify_email` и `confirm_email_change` оба
читают из `email_verification_tokens`; различает их только проверка
`user.pending_email` в confirm.

**Что не так.** Один тип токенов на две операции. Опасное направление
(использовать registration-токен для смены email) закрыто гардом
`pending_email`. Обратное (токен смены на `/verify-email`) лишь подтвердит email
— безвредно. Токены — непредсказуемые хеши, подделать нельзя.

**Фикс (опц.).** Добавить колонку `purpose` (`verify`/`email_change`) и сверять
её в каждом потребителе — строгое разделение на будущее.

---

### L3 — Глобальный passthrough санитизации по имени поля `content`  ·  Low

**Где.** `app/middleware/sanitization.py` — `RAW_HTML_FIELDS = {"content"}`
(добавлено в этапе 17).

**Что не так.** Любое поле тела с именем `content` глобально минует санитизацию
(сейчас единственный потребитель — блог, и он чистит своим allowlist'ом).
Если в будущем появится другой эндпоинт с полем `content`, ожидающий глобальную
очистку, он молча получит сырой ввод.

**Фикс (на будущее).** Привязать исключение к маршруту/схеме, а не к глобальному
имени поля (например, обрабатывать сырой HTML на уровне конкретного роутера, а
не в общем middleware), либо переименовать поле блога во что-то специфичное
(`body_html`) — когда/если конфликт станет реальным.

## План исправлений (фазовый)

### P0 — безопасные быстрые победы (низкий риск, высокая ценность)
1. **C1** — валидатор `secret_key` в `Settings` (fail-fast в prod) + задать ключ
   в `.env` окружения. *(меняет только конфиг + старт)*
2. **H1** — публичный read блога только `published`; draft под writer-роль. *(блог
   изолирован, покрыт тестами этапа 17 — добавить кейсы на видимость)*
3. **M1** — `check_rate_limit` на `GET /posts` (и `?query`); затем на тяжёлые
   публичные списки `dogs/kennels/litters`. *(паттерн уже есть в classifieds)*

### P1 — логика, требует аккуратности
4. **M2** — развязать in_app/email в `events_handler` (получатели in_app по
   in_app-подпискам). Нужны интеграционные тесты на оба канала + дедуп.

### P2 — уточнения/тех-долг
5. **L1** — решить про ownership на постах (фикс или документировать).
6. **L2** — колонка `purpose` для verify-токенов (миграция).
7. **L3** — пересмотреть passthrough санитизации, когда появится второй
   потребитель `content`.

### Каждый фикс — с тестом
Для P0/P1 сначала падающий тест на симптом (как в фиксе ghost badge), затем
исправление; `pytest -q` без регрессий.
