# Дизайн: генерация официальных документов выставки (формат РКФ)

**Дата:** 2026-05-29
**Статус:** утверждён к написанию плана
**Связано с:** этап 8 (`docs/plans/stages/stage-08-documents.md`)

## Контекст и цель

Организатор должен получать из платформы три документа в **точно том же**
формате, содержании и оформлении, что и образцы РКФ (исходники —
`Дипломы А4.rtf`, `Ринговая ведомость.rtf`, `САС 11 2025.rtf`):

1. **Диплом** — один на собаку, двуязычный (RU/EN), A4.
2. **Ринговая ведомость** — рабочий лист эксперта на ринг/породу/класс/пол;
   участники предзаполнены, колонки результата **пустые** (судья пишет от руки).
3. **Каталог выставки** — полный, по группам FCI → породам → классам → полу.

Содержание-брендинг (надписи «WORLD DOG SHOW 2025», «РОССИЙСКАЯ
КИНОЛОГИЧЕСКАЯ ФЕДЕРАЦИЯ», «WWW.RKF.ORG.RU» и т.п.) сохраняется как
литералы в шаблонах — на этой итерации не параметризуется.

В проекте уже есть подсистема генерации документов этапа 8
(`app/services/document.py`, `app/utils/pdf.py`,
`worker/handlers/document_handler.py`, `app/routers/documents.py`) с
минималистичной ReportLab-вёрсткой. **Этот функционал не удаляется и не
меняется** — официальные документы реализуются параллельно.

## Ключевые решения (из брейнсторма)

- Выход: **и редактируемый файл (DOCX), и PDF** (вариант 3).
- Старый функционал **дублируется**, а не заменяется.
- Движок: **DOCX-шаблоны + `docxtpl` + LibreOffice headless → PDF** (вариант A).
- ФИО людей: **добавить профиль с ФИО/страной**.
- Заводчик и владелец **разделяются сразу** (а не упрощаются).
- Объём первой итерации: **все три документа сразу**.

## Раздел 1. Изменяемые поля (результат парсинга образцов)

### Диплом (1 на собаку)

| Поле бланка | Источник |
|---|---|
| Выставка / DOG SHOW | `Show.name` |
| Эксперт / JUDGE | ФИО судьи + страна |
| Порода / BREED | `Breed.name` |
| Пол (КОБЕЛИ/СУКИ) | `Dog.sex` (отметка нужного) |
| Класс / CLASS | `ShowClass.name` |
| Оценка / GRADE | `Grade.name` (из `ShowResult.grade_id`) |
| Титул / TITLE | титулы из `ShowResult.titles_cache` |
| Место / PLACE | `ShowResult.placement` |
| Кличка / NAME | `Dog.name` |
| № клейма / TATTOO | `Dog.tattoo` |
| № чипа / MICROCHIP | `Dog.microchip` |
| Дата рождения / DATE OF BIRTH | `Dog.date_of_birth` |
| Владелец / OWNER | ФИО владельца (`Dog.kennel.owner`) |
| Питомник / KENNEL | приставка заводчика (`Dog.breeder_kennel.kennel_prefix`) |
| Заводчик / BREEDER | ФИО заводчика (см. резолв ниже) |
| Родословная № / PEDIGREE | `Dog.rkf_number` |

Диплом может генерироваться «пустым» (бланк с точками) до ввода
результата — отсутствующие поля рендерятся пустыми, не валят генерацию.

### Ринговая ведомость (на ринг + порода + класс + пол)

- **Шапка:** регион/город (`Show.city`), дата (`ShowRing.ring_date` →
  fallback `Show.date_start`), эксперт (ФИО + страна), порода
  (`Breed.name`), № ринга (`ShowRing.ring_number`), класс, пол.
- **Строки (на собаку):** № кат. (`ShowEntry.catalog_number`),
  кличка + дата рожд. + окрас, № родословной + клеймо/чип,
  заводчик + владелец.
- **Пустые колонки (судья заполняет от руки):** Оценка, Звания/титулы,
  Место, Выводок, Сумма.

### Каталог (весь по группам FCI → породы → классы → пол)

- **Шапка:** название/ранг/даты/место выставки, список судей с
  назначениями.
- **На породу:** назначенный судья.
- **На запись:** № кат., кличка, дата рожд., окрас, родословная №,
  клеймо/чип, заводчик, владелец, родители (отец `Dog.father` / мать
  `Dog.mother`).

Каталог формируется до выставки — без оценок и титулов.

## Раздел 2. Изменения модели данных

### 2.1. Профиль пользователя (ФИО/страна)

Новая таблица `UserProfile` (1:1 к `User`, `ON DELETE CASCADE`):

| Колонка | Тип | Прим. |
|---|---|---|
| user_id | UUID PK/FK→users.id | один профиль на юзера |
| last_name | VARCHAR(128) NULL | фамилия |
| first_name | VARCHAR(128) NULL | имя |
| patronymic | VARCHAR(128) NULL | отчество |
| country | VARCHAR(64) NULL | страна (для «(Россия)» у эксперта) |

- Хелпер `full_name(profile)` → «Фамилия Имя Отчество», пустые части
  опускаются; fallback на `User.email`, если профиль пуст.
- Хелпер `judge_display(profile)` → «Фамилия Имя (Страна)».
- `_user_display` в `document.py` переключается на этот хелпер.
- Alembic-миграция; поля в схемах и роутере `users` (GET/PATCH профиля),
  чтобы данные можно было заполнять.

### 2.2. Разделение «заводчик ≠ владелец»

На `Dog` добавляются:

| Колонка | Тип | Прим. |
|---|---|---|
| breeder_kennel_id | UUID NULL, FK→kennels.id, `ON DELETE SET NULL` | питомник, где рождена собака; неизменен при продаже |
| breeder_name | VARCHAR(255) NULL | free-text fallback для заводчиков вне платформы (импорт) |

Существующий `Dog.kennel_id` = **текущий питомник владельца** (меняется
при продаже).

**Резолв полей документа:**
- **Владелец** = `full_name(Dog.kennel.owner.profile)`.
- **Заводчик** = `full_name(Dog.breeder_kennel.owner.profile)`; если
  `breeder_kennel_id` пуст → `Dog.breeder_name`; иначе пусто.
- **Питомник (графа KENNEL)** = `Dog.breeder_kennel.kennel_prefix`.

**Плюсы:** корректная семантика РКФ (заводчик фиксируется навсегда);
переживает смену владельца; импорт покрыт free-text; связь
переиспользуется в родословной/карточке.
**Минусы:** +колонка/миграция/бэкофилл (у текущих собак `NULL` →
заводчик пустой, пока не дозаполнят); поле надо заполнять при заведении
собаки; +1 join в билдере (некритично).

**Тех-долг:** модель `Litter` уже есть (`kennel_id`, `father_id`,
`mother_id`), но у `Dog` нет ссылки на помёт. Когда появится связь
`Dog.litter_id`, добавить автозаполнение
`breeder_kennel_id = dog.litter.kennel_id`.

### 2.3. Достаточные существующие поля

`Dog.tattoo`, `Dog.microchip`, `Dog.rkf_number`, `Dog.color`,
`Dog.date_of_birth`, `ShowClass`, `Grade`, титулы, `ShowRing`
(№ ринга, дата) — уже есть, изменений не требуют.

## Раздел 3. Архитектура

Всё новое — рядом со старым, без правок существующих модулей генерации.

- **`app/templates/documents/`** — три DOCX-шаблона
  (`diploma.docx`, `ring_sheet.docx`, `catalog.docx`) с плейсхолдерами
  `docxtpl` (`{{ field }}`) и табличными циклами
  (`{%tr for row in rows %}`). RTF-образцы один раз конвертируются в DOCX
  и размечаются вручную с сохранением оформления.
- **`app/services/document.py`** — *дополняется* функциями сбора
  контекста-словаря для docxtpl:
  `build_official_catalog_context`, `build_official_diploma_context`,
  `build_ring_sheet_context`. Существующие DTO/билдеры не трогаются.
- **`app/utils/docx_render.py`** — *новый* модуль:
  `render_docx(template_path, context) -> bytes` (docxtpl) и
  `convert_to_pdf(docx_bytes) -> bytes`. Конвертер — тонкая обёртка с
  выбором бэкенда: LibreOffice headless (`soffice --headless
  --convert-to pdf`), на Windows-dev — fallback на Word COM.
  `app/utils/pdf.py` не изменяется.
- **`worker/handlers/document_handler.py`** — *дополняется* ветками
  диспетчера по новым `task.type` (старые ветки без изменений).
- **`app/schemas/task.py`** — новые значения `DocumentKind`:
  `catalog_docx`, `diploma_docx`, `diplomas_batch_docx`,
  `ring_sheet_docx`. Формат вывода (`docx`/`pdf`) — поле в payload.

**Поток:** API создаёт Task(pending) → публикует в RabbitMQ → воркер
собирает контекст из БД → `render_docx` → при `format=pdf` ещё
`convert_to_pdf` → upload в MinIO → `mark_done(file_id)`. Реиспользуется
существующая инфраструктура Task/MinIO/статус-машины.

## Раздел 4. API (новые ручки; старые остаются)

| Метод | Путь | Назначение |
|---|---|---|
| POST | `/shows/{id}/official/catalog?format=docx\|pdf` | каталог РКФ |
| POST | `/shows/{id}/official/diplomas?format=docx\|pdf` | пакет дипломов |
| POST | `/shows/{id}/entries/{eid}/official/diploma?format=docx\|pdf` | один диплом |
| POST | `/shows/{id}/official/ring-sheets?format=docx\|pdf&ring_id=` | ведомости (все ринги или один) |
| GET | `/shows/{id}/official/{kind}/context` | собранные данные документа в JSON (предпросмотр/правка на фронте) |
| GET | `/shows/{id}/documents/readiness` | чек-лист пробелов (собаки без клейма, участники без ФИО владельца/заводчика) до печати |

Доступ — organizer/admin (как в существующем `documents.py`). Возвращают
`TaskResponse` (202) как старые ручки; результат скачивается через
существующий `/tasks/{id}/download`.

## Раздел 5. Тестирование

- Unit на билдеры контекста: структура словаря, группировка/сортировка
  (группы FCI → породы → классы → пол), резолв заводчик/владелец,
  пустые поля (нет результата, нет заводчика).
- Unit на хелперы `full_name` / `judge_display` (пустые части, fallback
  на email).
- Тест `render_docx` на фиктивном контексте: файл генерится, не падает
  на спецсимволах в кличках/именах.
- `convert_to_pdf` мокается в тестах (LibreOffice отсутствует в CI);
  сам конвертер изолирован как тонкая обёртка.

## Раздел 6. Риски и эксплуатация

- **LibreOffice в Docker** — вес образа и настройка headless; учитывается
  в Dockerfile на этапе 15. До этого PDF на dev — через Word COM fallback.
- **Бэкофилл** `breeder_kennel_id`/профилей — старые данные неполны;
  `readiness`-ручка помогает организатору дозаполнить.
- **Точность вёрстки** зависит от ручной разметки DOCX-шаблонов —
  проверяется визуально на реальных данных, не автотестом.
