# Телефон — основной способ регистрации и входа

**Дата:** 2026-10-01
**Затрагивает:** `show-ring-backend`, `show-ring-frontend`
**Статус:** реализовано (BE-1…BE-6, FE-1…FE-8), самопроверка — раздел 8, итоги проверки — раздел 9

---

## 1. Бизнес-требование

1. Основной способ регистрации и входа — **номер телефона** пользователя.
2. Зарегистрироваться можно **только** подтвердив свой телефон (владение номером доказывается SMS-кодом).
3. Вход по почте — **дополнительный**, не основной: его можно подключить к уже существующему аккаунту.
4. Система должна быть **расширяемой**: в будущем появятся другие способы (VK ID, Telegram, Яндекс ID, Госуслуги и т.п.).
5. Фронтенд адаптируется под новые требования.

## 2. Как устроено сейчас (as-is)

### 2.1 Бэкенд

| Что | Где | Состояние |
|---|---|---|
| Регистрация по email+паролю | `POST /auth/register` → `services/auth.register_user` | Создаёт юзера, шлёт письмо подтверждения. **Равноправный** способ регистрации. |
| Вход по email+паролю | `POST /auth/login`, `POST /auth/token` (Swagger) | Работает, вход с неподтверждённой почтой разрешён (продуктовое решение). |
| Вход/регистрация по телефону (OTP) | `POST /auth/send-code`, `POST /auth/verify-code` → `services/otp_auth.py` | **Уже реализовано** (план `docs/plans/2026-06-10-phone-otp-auth.md`): find-or-create по номеру, коды в Redis (SHA-256), cooldown 60 с, 3 попытки, суточный лимит 10 SMS на номер, `is_phone_verified=True`. |
| SMS-провайдер | `services/sms.py` | Абстракция `SMSProvider` + `MockSMSProvider` + `SmsRuProvider`, DI через `Depends(get_sms_provider)`. |
| Токены | `issue_token_pair`, `_deliver_tokens` | Общие для всех способов: httpOnly-куки (веб) или тело (`X-Token-Delivery: body`, мобильный). |
| Модель | `models/user.py` | `email` и `hashed_password` nullable, `phone` (E.164, unique), CHECK `email IS NOT NULL OR phone IS NOT NULL`, `is_phone_verified`. |
| Смена email | `PUT /users/me` + `POST /auth/confirm-email-change` | Требует **текущий пароль** → телефонный пользователь (без пароля) не может добавить почту. |
| Смена пароля | `PUT /users/me/password` | Требует текущий пароль → телефонному пользователю недоступна. |

### 2.2 Фронтенд

- Используется только метод `jwt` (`src/global-config.ts`), страницы `/auth/jwt/sign-in` и `/auth/jwt/sign-up`.
- Оба экрана — **только email+пароль**. Эндпоинты `/auth/send-code` и `/auth/verify-code` фронтом не используются.
- В UI-ките уже есть `Field.Phone` (react-phone-number-input) и `Field.Code` (OTP-поле на 6 ячеек), `FormResendCode`.
- Профиль → «Безопасность»: карточки «Сменить email» (с текущим паролем) и «Сменить пароль».
- Отображение имени пользователя (`getUserDisplay`, профиль) опирается на `user.email` — у телефонного пользователя будет пусто.

### 2.3 Разрыв с требованием

| Требование | Разрыв |
|---|---|
| Телефон — основной | Фронт вообще не умеет входить по телефону. |
| Регистрация только по телефону | `POST /auth/register` по email открыт; фронт регистрирует только по email. |
| Email — дополнительный | Телефонный пользователь не может добавить email-вход (все операции требуют пароль, которого нет). |
| Расширяемость | Способы входа захардкожены в роутере/фронте, клиент не знает, какие методы включены. OTP-сервис умеет только одну цель — вход. |
| Старые пользователи | У зарегистрированных по email нет телефона, способа его привязать нет. |
| Технический долг | Письма-уведомления (`email_change_notice`, `password_changed`) уходят на `user.email`, который у телефонных юзеров `None`; документы показывают `None` вместо имени. |

## 3. Варианты реализации

### Вариант A — Phone-first поверх текущей модели (рекомендуется)

Оставляем `users.phone`/`users.email` как канонические контакты. Добавляем:
- **реестр способов аутентификации** в коде (`services/auth_methods.py`) + публичный `GET /auth/methods` — фронт рисует экраны по нему;
- **цели OTP** (`login` / `reauth` / `link_phone`) — один OTP-движок для входа, подтверждения чувствительных действий и привязки номера;
- закрываем email-регистрацию флагом (`AUTH_EMAIL_REGISTRATION_ENABLED=false` по умолчанию), email-вход оставляем;
- эндпоинты «привязать телефон» (для старых email-пользователей) и «подключить вход по почте» (для телефонных).

**Плюсы:** минимальные изменения схемы (миграций нет — колонки уже есть), переиспользует готовый OTP/SMS-слой и токены, не ломает существующих пользователей, мобильный клиент и e2e. Реестр методов + цели OTP дают точку расширения.
**Минусы:** при появлении OAuth-провайдеров понадобится таблица внешних идентичностей (см. 3.2 — спроектировано, но не внедряется сейчас). Email и телефон остаются колонками `users`, а не равноправными «идентичностями».

### Вариант B — Таблица идентичностей `user_identities`

`user_identities(id, user_id, provider, provider_uid, secret_hash, verified_at)`: телефон, email, VK и т.д. — строки одной таблицы; `users.email/phone/hashed_password` переносятся туда.

**Плюсы:** максимальная расширяемость, единообразие, несколько телефонов/почт на аккаунт.
**Минусы:** большая миграция данных; переписывание всех мест, где читается `user.email` (письма, документы, админка, уведомления, ~15 точек); двойной источник правды на время перехода; высокий риск регрессий в уже отлаженном auth (аудиты 2026-05/06). Для текущего набора методов (телефон + email) — overkill.

### Вариант C — Внешний Identity Provider (Firebase Phone Auth / Supabase / Keycloak / Auth0)

В шаблоне фронта даже лежат контексты firebase/supabase/auth0.

**Плюсы:** готовые SMS, антифрод, OAuth-провайдеры «из коробки».
**Минусы:** vendor lock-in; 152-ФЗ (хранение ПДн граждан РФ за рубежом), нестабильная доставка SMS в РФ у зарубежных IdP; ломается собственный JWT/cookie-пайплайн, RBAC в токене, refresh-rotation; стоимость; потеря контроля над антифродом. Отвергнут.

### Вариант D — Альтернативные каналы доставки кода (flash-call, Telegram Gateway, WhatsApp)

Не отдельная архитектура, а **расширение варианта A**: `SMSProvider` уже абстракция; flash-call / Telegram Gateway добавляются как новые реализации канала доставки без изменения бизнес-логики. В рамках этой задачи не реализуются — зафиксированы как точка расширения.

### 3.1 Сравнение

| Критерий | A | B | C |
|---|---|---|---|
| Объём работ | малый–средний | большой | большой |
| Миграция данных | нет | да, рискованная | да (перенос юзеров) |
| Риск регрессий | низкий | высокий | высокий |
| Расширяемость под OAuth | средняя (+таблица позже) | высокая | высокая |
| 152-ФЗ / контроль | полный | полный | проблемы |
| Стоимость владения | SMS | SMS | SMS + подписка |

**Решение: вариант A**, с заранее спроектированным путём к OAuth (3.2).

### 3.2 Путь расширения (не реализуется сейчас)

Добавление, например, VK ID:
1. Таблица `user_external_identities(user_id, provider, provider_uid, created_at, UNIQUE(provider, provider_uid))` — только для внешних провайдеров; телефон/email остаются в `users`.
2. Новый метод в реестре `auth_methods` (`id="vk_id"`, `sign_in=True`, `sign_up=True`).
3. Колбэк провайдера: если идентичность привязана — `issue_token_pair`; если нет — выдаётся короткоживущий `registration_ticket` (Redis, 10 мин), и фронт ведёт пользователя на шаг **«подтвердите телефон»** (`/auth/send-code` + `/auth/verify-code` с `registration_ticket`). Так требование «регистрация только по своему телефону» сохраняется для любого будущего способа.
4. Фронт рисует кнопку провайдера из `GET /auth/methods` — без правок экранов.

## 4. Спецификация (вариант A)

### 4.1 Термины

- **Телефонный пользователь** — создан через OTP, `email IS NULL`, `hashed_password IS NULL` до подключения email-входа.
- **Legacy-пользователь** — создан через email-регистрацию до этой задачи, `phone IS NULL`.
- **Цель OTP (purpose)** — для чего выдан код: `login`, `reauth`, `link_phone`. Код одной цели не принимается в другой.

### 4.2 Бэкенд

#### 4.2.1 Настройки (`app/config.py`)

| Настройка | Дефолт | Смысл |
|---|---|---|
| `auth_email_login_enabled` | `True` | Вход по email+паролю (дополнительный способ). |
| `auth_email_registration_enabled` | `False` | Регистрация по email. Выключена: регистрация только по телефону. Оставлена флагом для отката. |
| `auth_phone_required` | `True` | Каждый аккаунт должен иметь подтверждённый телефон. Отдаётся клиенту; фронт просит legacy-пользователей привязать номер. |

#### 4.2.2 Реестр способов: `GET /auth/methods` (публичный)

```json
{
  "primary": "phone_otp",
  "phone_required": true,
  "methods": [
    {"id": "phone_otp", "sign_in": true, "sign_up": true},
    {"id": "email_password", "sign_in": true, "sign_up": false}
  ]
}
```

- Порядок `methods` — порядок показа; `primary` — метод по умолчанию.
- Метод с `sign_in=false` и `sign_up=false` в ответ не попадает.
- `phone_otp` всегда включён (основной способ, не отключается флагом).

#### 4.2.3 Закрытие email-регистрации

- `POST /auth/register` при `auth_email_registration_enabled=False` → **403** `registration_method_disabled` (rate-limit проверяется до этого, как и раньше).
- `POST /auth/login` и `POST /auth/token` при `auth_email_login_enabled=False` → **403** `login_method_disabled`.
- `POST /auth/resend-verification` остаётся (нужен legacy-пользователям).

#### 4.2.4 Цели OTP (`services/otp_auth.py`)

```python
class OTPPurpose(str, Enum):
    login = "login"           # вход/регистрация, код на вводимый номер
    reauth = "reauth"         # подтверждение чувствительного действия, код на номер аккаунта
    link_phone = "link_phone" # привязка номера к аккаунту, код на новый номер
```

Ключи Redis:

| Ключ | TTL | Зачем |
|---|---|---|
| `otp:{purpose}:code:{subject}` | `otp_code_ttl_seconds` | SHA-256 кода |
| `otp:{purpose}:attempts:{subject}` | как у кода | счётчик попыток |
| `otp:{purpose}:cooldown:{phone}` | `otp_send_cooldown_seconds` | пауза между отправками на номер в рамках цели |
| `otp:daily:{phone}` | 86400 | общий суточный лимит SMS на номер (все цели — защита бюджета) |

`subject` — к чему привязан код:
- `login` → номер телефона;
- `reauth` → `user_id`;
- `link_phone` → `{user_id}:{phone}` (код, полученный одним пользователем, не подходит другому, и подходит только к тому номеру, на который отправлен).

API сервиса:
- `send_otp_code(redis, sms, phone, *, purpose=login, subject=None)` — subject по умолчанию = phone. Текст SMS зависит от цели («Ваш код входа: …», «Код подтверждения: …», «Код для привязки номера: …»).
- `consume_otp_code(redis, code, *, purpose, subject)` — проверка + одноразовое сжигание, бросает `OTPExpiredError` / `OTPInvalidError`. Логика попыток — текущая (3 попытки, атомарный INCR, атомарный DEL на успехе).
- `verify_otp_code(db, redis, phone, code)` — вход: `consume(purpose=login)` + find-or-create + токены. Возвращает `(TokenResponse, is_new_user)`.

Ключи меняют формат (`otp:code:{phone}` → `otp:login:code:{phone}`): коды, выданные за ≤5 минут до деплоя, перестанут приниматься — пользователь запросит новый. Допустимо.

#### 4.2.5 Ответ входа по телефону

`POST /auth/verify-code` → `TokenResponse` получает поле `is_new_user: bool = False` (`true`, если аккаунт создан этим запросом). Фронт ведёт нового пользователя в профиль дозаполнить ФИО. Раскрытие «новый/старый» после подтверждения владения номером — не enumeration.

#### 4.2.6 Привязка телефона (legacy-пользователи) — авторизованные эндпоинты

`POST /users/me/phone/send-code` `{phone}`:
- у пользователя уже есть подтверждённый телефон → **409** `phone_already_set` (смена номера — отдельная будущая задача, сейчас через поддержку);
- номер занят другим аккаунтом → **409** `phone_taken` (проверка до отправки SMS — экономим деньги; эндпоинт под авторизацией и rate-limit, поэтому enumeration ограничен);
- иначе — `send_otp_code(purpose=link_phone, subject=f"{user.id}:{phone}")`; ответ `{"message": "Код отправлен"}`.
- Rate-limit по IP 5/60 + cooldown/daily OTP. 429/502 — как у `/auth/send-code`.

`POST /users/me/phone/verify` `{phone, code}`:
- `consume_otp_code(purpose=link_phone, subject=f"{user.id}:{phone}")`;
- ошибки кода → **400** `code_expired` / **400** `invalid_code` (**не 401**: фронтовый axios-интерсептор трактует 401 на не-`/auth/` URL как протухшую сессию и пытается refresh/редирект);
- `phone_already_set` → 409; запись `phone`, `is_phone_verified=True`; `IntegrityError` (номер заняли параллельно) → 409 `phone_taken`;
- аудит `phone_linked`; ответ — `UserResponse`.

#### 4.2.7 Подключение входа по почте (телефонные пользователи)

`POST /users/me/reauth/send-code` (без тела):
- нет подтверждённого телефона → **409** `phone_not_set`;
- `send_otp_code(phone=user.phone, purpose=reauth, subject=str(user.id))`.

`POST /users/me/email-login` `{email, password, code}`:
- у пользователя уже есть `email` → **409** `email_already_set` (для смены — существующий `PUT /users/me`);
- `consume_otp_code(purpose=reauth, subject=user.id)` → 400 `code_expired`/`invalid_code` (re-auth вместо пароля: украденная access-кука без телефона не позволит повесить на аккаунт чужую почту);
- email занят другим аккаунтом → **409** `email_taken`;
- `hashed_password = hash(password)` (политика паролей та же, что при регистрации), `pending_email = email`, токен подтверждения `purpose=email_change`, письмо `email_change_confirm` на новый адрес, аудит `email_login_requested`;
- ответ `{"message": "Проверьте почту для подтверждения"}`.
- Вход по почте начинает работать **после клика по ссылке** (`/auth/confirm-email-change` переносит `pending_email` → `email`). Пока не подтверждено, повторный запрос разрешён (email всё ещё `NULL`) и перезаписывает пароль и `pending_email` — так исправляется опечатка в адресе.
- Подтверждение по-прежнему отзывает все refresh-токены (поведение `confirm_email_change` не меняется) — пользователь входит заново телефоном или почтой.

#### 4.2.8 Устойчивость к `email IS NULL`

- `request_email_change`: уведомление на старый адрес — только если `user.email` есть.
- `change_password`: письмо-уведомление — только если `user.email` есть.
- `UserResponse` получает `has_password: bool` и `pending_email: str | None` (собственные данные пользователя, `GET /users/me`). `has_password` — свойство модели `User`.
- `utils/names.full_name` и `services/document._user_display`: fallback `email → phone`.

#### 4.2.9 Что не меняется

- `/auth/send-code`, `/auth/verify-code` — тот же контракт (+ поле `is_new_user`).
- Доставка токенов (куки / `X-Token-Delivery: body`), refresh-rotation, logout.
- Миграции БД не нужны.

### 4.3 Фронтенд

#### 4.3.1 API-слой
- `endpoints.auth`: `methods`, `sendCode`, `verifyCode`, `phoneSendCode`, `phoneVerify`, `reauthSendCode`, `emailLogin`.
- `src/auth/context/jwt/action.ts`: `sendPhoneCode(phone)`, `verifyPhoneCode(phone, code) → { isNewUser }`.
- `src/actions/account.ts`: `sendLinkPhoneCode`, `verifyLinkPhone`, `sendReauthCode`, `addEmailLogin`; `IMe` += `phone`, `is_phone_verified`, `has_password`, `pending_email`, `email: string | null`.
- `src/auth/hooks/use-auth-methods.ts`: SWR `GET /auth/methods` с **fallback-значением** (телефон основной + email-вход) — экран рисуется сразу, без мигания.

#### 4.3.2 Телефон
- `src/auth/phone.ts`: `phoneSchema(messages)` (zod, `isValidPhoneNumber` из `react-phone-number-input`), `codeSchema`, маппинг машинных кодов ошибок OTP в i18n-ключи (`resolveOtpError`). Покрыт vitest.
- Компонент `PhoneOtpForm` (`src/auth/components/phone-otp-form.tsx`), двухшаговый:
  1. `Field.Phone` (страна по умолчанию RU) → «Получить код»;
  2. `Field.Code` (6 цифр), «Изменить номер», «Отправить код повторно» с обратным отсчётом 60 с (`useCountdownSeconds`).
  - Пропсы: `submitLabel`, `onVerified(isNewUser)`. Используется на входе и регистрации.

#### 4.3.3 Экраны
- **Вход** (`/auth/jwt/sign-in`): по умолчанию — телефон. Ссылка «Войти по почте» (если метод включён) переключает на текущую email-форму, «Войти по телефону» — обратно. `?method=email` открывает email-форму сразу (deep-link, e2e). Под формой телефона — текст согласия (вход с новым номером создаёт аккаунт).
- **Регистрация** (`/auth/jwt/sign-up`): только `PhoneOtpForm` + согласие с условиями. Email-форма удалена.
- После успеха: `isNewUser` → полная навигация в `/dashboard/profile` (заполнить ФИО); иначе — текущий флоу (`checkUserSession` + `router.refresh`).

#### 4.3.4 Профиль → «Безопасность»
- **Телефон**: подтверждённый номер (только просмотр) или форма привязки (номер → код).
- **Вход по почте**:
  - `email` пуст → «Подключить вход по почте»: email, пароль, повтор → «Получить код по SMS» → код → отправить; если есть `pending_email` — подсказка «ожидает подтверждения: …».
  - `email` есть → текущая карточка смены email.
- **Пароль**: карточка смены пароля только при `has_password`.

#### 4.3.5 Legacy-пользователи
- В дашборде — баннер «Привяжите номер телефона» (ссылка на «Безопасность»), если `phone_required` и `!is_phone_verified`. Мягкое принуждение: старые аккаунты не блокируются.

#### 4.3.6 Отображение
- `getUserDisplay`: fallback `имя → email → phone`; профиль показывает email или телефон, бейдж «Телефон подтверждён».

#### 4.3.7 i18n
- Новые ключи в `ru/auth.json`, `en/auth.json`, `ru/profile.json`, `en/profile.json`.

#### 4.3.8 e2e
- `e2e/auth.setup.ts` открывает `/auth/jwt/sign-in?method=email` (сид-админ — email-пользователь).

## 5. Сложности интеграции и риски

| Риск | Митигация |
|---|---|
| **SMS-pumping** (перебор номеров ради списания денег) | Уже есть: IP-лимит, cooldown на номер, суточный лимит. Новые эндпоинты — под авторизацией + те же лимиты; `phone_taken` проверяется до отправки SMS. |
| **Доставка SMS в РФ** (регистрация имени отправителя, блокировки) | Абстракция провайдера; flash-call / Telegram Gateway как будущие каналы (вариант D). |
| **Номер уже принадлежит другому аккаунту** (у человека есть и старый email-аккаунт, и новый телефонный) | 409 `phone_taken` + текст «обратитесь в поддержку». Слияние аккаунтов — отдельная задача. |

| **Захват аккаунта украденной сессией** | Подключение email-входа требует свежий OTP на номер аккаунта (`reauth`). |

| **e2e и сиды работают через email** | Email-вход сохраняется; `?method=email`; в интеграционных тестах email-регистрация включается фикстурой. |

| **Ключи OTP меняют формат** | Только коды, выданные ≤5 мин до деплоя; пользователь запросит новый. |
| **152-ФЗ** | Телефон — ПДн; хранится в своей БД (РФ), в логах prod — без кодов (уже так). |

## 8. Самопроверка спеки

Проверено на противоречия и дыры; найденное исправлено в тексте выше:

1. **401 vs интерсептор.** Первоначально OTP-ошибки на `/users/me/*` планировались 401 (как на `/auth/verify-code`). Фронтовый интерсептор на 401 вне `/auth/` делает refresh и редирект на логин — пользователь вылетел бы из сессии за опечатку в коде. → 400.
2. **Ключ `link_phone` без user_id.** Если subject = только номер, два пользователя, привязывающих один номер, перетирали бы коды друг друга. → `subject = {user_id}:{phone}`.
3. **Общий cooldown для всех целей.** Пользователь, только что вошедший по SMS, не смог бы минуту подключить почту (429). → cooldown на (цель, номер), а суточный лимит — общий на номер (защита бюджета сохраняется).
4. **Тупик с опечаткой в email.** Условие «email-вход можно подключить, только если нет пароля» не дало бы исправить опечатку до подтверждения (пароль уже установлен). → условие «`email IS NULL`», повторный запрос перезаписывает `pending_email` и пароль.
5. **Регистрация «тихо» на экране входа.** Вход по неизвестному номеру создаёт аккаунт (find-or-create) — значит согласие с условиями нужно показывать и на экране входа по телефону. → добавлено в 4.3.3.
6. **e2e.** Скрытие email-формы по умолчанию сломало бы `auth.setup.ts`. → `?method=email`.
7. **Интеграционные тесты** массово регистрируют пользователей через `/auth/register`. Выключение флага без фикстуры сломало бы ~30 тестов. → autouse-фикстура (BE-2).
8. **`confirm_email_change` и телефонный пользователь.** Перенос `pending_email → email` работает и при `email IS NULL`; отзыв сессий ожидаем, фронт уже отрабатывает его (`resetRevokedSession`). Письмо-уведомление «старому адресу» в этом сценарии не нужно — его отправляет только `request_email_change`, который тут не вызывается. Противоречий нет.
9. **Принуждение legacy-пользователей.** Жёсткая блокировка без телефона сломала бы e2e и вход сид-админа и не следует из требования (оно про регистрацию). → мягкий баннер, жёсткое — FUT-5.
10. **`phone_otp` нельзя выключить.** Иначе регистрация стала бы невозможна при выключенной email-регистрации. Зафиксировано в 4.2.2.
11. **Дубликат аккаунта у legacy-пользователя.** Экран входа по умолчанию — телефон. Legacy-пользователь (телефона в аккаунте нет) вводит свой номер → find-or-create создаёт **второй, пустой** аккаунт; потом привязать номер к старому аккаунту нельзя (`phone_taken`). Полностью это решает только слияние (FUT-2), но снижаем вероятность: (а) на экране входа под формой телефона — подсказка «Регистрировались по почте? Войдите по почте и привяжите телефон в профиле»; (б) если `/auth/verify-code` вернул `is_new_user=true` на экране **входа** (не регистрации), после перехода в профиль показывается уведомление «Создан новый аккаунт. Если у вас уже был аккаунт по почте — выйдите и войдите по почте». Добавлено в FE-4.
12. **Сигнатура `verify_otp_code`** меняется на `(tokens, is_new_user)` — существующие unit-тесты `test_otp_auth.py` и интеграционный `test_phone_auth_flow.py` обновляются в BE-3.
